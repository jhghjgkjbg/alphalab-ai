# Collector Framework

Collector Framework определяет единую границу поступления внешних данных в Alpha Core. Он задаёт контракт будущих Collectors, базовые типы результата и явный registry доступных реализаций.

Фреймворк не получает данные самостоятельно. В TASK-0005 отсутствуют сетевые клиенты, API, парсеры, адаптеры источников и интеграция с Knowledge.

## Как будет происходить сбор данных

1. Внешний composition root создаёт Collector и передаёт ему необходимые адаптеры через будущий механизм конфигурации.
2. Оркестратор вызывает асинхронный метод `collect()`.
3. Collector обращается к одному типу источника через разрешённый входной адаптер.
4. Полученные данные преобразуются в `SourceItem` без доменной интерпретации.
5. Collector возвращает единый `CollectorResult` с итоговым статусом, элементами и диагностикой ошибок.
6. Следующий слой публикует результат как версионированное событие; Knowledge потребляет событие через собственный публичный контракт.

Конкретные адаптеры, события и механизм запуска будут определены отдельными Backlog-задачами.

## Контракт BaseCollector

Каждый Collector обязан:

- наследовать `BaseCollector`;
- предоставлять стабильное уникальное имя через `name()`;
- реализовывать `async collect()`;
- возвращать `CollectorResult` при ожидаемом завершении сбора;
- сохранять идентификатор источника и время получения каждого `SourceItem`;
- отделять исходный `payload` от служебных `metadata`;
- сообщать частичный результат явно через `CollectorStatus.PARTIAL`;
- быть пригодным для создания и управления внешним composition root.

## Типы

- `SourceItem` — единица данных в форме, пригодной для передачи следующему слою;
- `CollectorResult` — итог одного запуска Collector;
- `CollectorStatus` — `success`, `partial` или `failed`.

Типы являются transport-neutral и не содержат моделей HTTP, базы данных или Knowledge.

## Registry

`CollectorRegistry` хранит соответствие стабильного имени и класса Collector. Registry позволяет:

- зарегистрировать класс Collector;
- получить зарегистрированный класс по имени;
- получить read-only snapshot всех регистраций.

Registry не создаёт экземпляры, не запускает сбор, не управляет зависимостями и не является глобальным singleton. Владелец процесса самостоятельно определяет его жизненный цикл.

## Что Collector не имеет права делать

Collector запрещено:

- интерпретировать данные как каноническое знание;
- рассчитывать score или принимать решения о публикации;
- напрямую вызывать `knowledge`, `scoring`, `workflow` или `publication`;
- управлять расписанием и повторными запусками;
- обращаться к базе данных, Redis или внутренним хранилищам Alpha Core;
- зависеть от FastAPI, backend, agents, workers или конкретного брокера событий;
- содержать учетные данные либо читать секреты из глобального состояния;
- скрывать частичные результаты и ошибки;
- регистрировать себя через побочный эффект импорта;
- передавать наружу модели конкретного SDK или транспорта.

## Файлы

- `base.py` — абстрактный контракт Collector;
- `types.py` — нейтральные типы входных элементов и результата;
- `registry.py` — локальный registry классов Collector.

Архитектурные правила и жизненный цикл подробно описаны в `docs/architecture/collector.md`.
