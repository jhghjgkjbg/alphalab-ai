# Архитектура Alpha Core

## Статус документа

- Backlog-задача: TASK-0004.
- Статус: начальная архитектурная граница.
- Реализация: отсутствует.

## Что такое Alpha Core

Alpha Core — защищенное, технологически независимое ядро AlphaLab AI. Оно определяет доменные границы и поток обработки информации от приема данных до публикации результата. Ядро не является частью FastAPI backend, агента, worker-процесса или инфраструктурного адаптера.

`core/` на текущем этапе — только пространство архитектурных модулей. Пустые `__init__.py` обозначают Python-пакеты, а README фиксируют ответственность. Наличие каталога не означает существование готового контракта или реализации.

## Модули

| Модуль | Ответственность |
| --- | --- |
| `event_bus` | Абстракция публикации и доставки доменных событий. |
| `collector` | Прием, первичная проверка и нормализация входных данных. |
| `knowledge` | Каноническое представление, происхождение и актуальность знания. |
| `scoring` | Воспроизводимое вычисление оценок на основе знания. |
| `publication` | Подготовка одобренного результата к передаче внешним каналам. |
| `scheduler` | Формирование временных триггеров запуска. |
| `workflow` | Координация стадий процесса через публичные порты и события. |

`source_manager` является application-границей запуска источников: он связывает SourceDefinition и CollectorRegistry, но не входит в доменную обработку Knowledge/Scoring.

## Модель взаимодействия

Модули взаимодействуют только через явно определенные, версионируемые контракты: команды, события и публичные порты. Реализации одного модуля не должны импортироваться другим модулем.

- `collector` принимает данные от внешнего адаптера и сообщает о результате приема.
- `knowledge` реагирует на принятые данные, формирует каноническое знание и сообщает об изменении.
- `scoring` получает согласованный снимок знания, рассчитывает оценку и выпускает результат оценки.
- `workflow` реагирует на события и координирует переход между допустимыми стадиями.
- `publication` получает только одобренный публикационный пакет и сообщает результат передачи.
- PublicationPolicy принимает решение на основании score, а Publisher выполняет только доставку выбранного candidate.
- `scheduler` формирует триггер, который инициирует workflow, но не выполняет его шаги.
- в AI Scout MVP scheduler callback вызывает SourceManager напрямую до появления Workflow Engine;
- `event_bus` переносит события и не интерпретирует их доменный смысл.

Конкретный синхронный или асинхронный транспорт пока не выбран. Решение о брокере, хранении и доставке является инфраструктурным и принимается отдельным ADR.

## Поток данных

```text
Внешний источник
      |
      v
  Collector
      |
      | событие о принятых данных
      v
  Knowledge
      |
      | версионированное знание
      v
   Scoring
      |
      | результат оценки
      v
   Workflow ---- решение о допустимом переходе ----> Publication
      ^                                                |
      |                                                v
  Scheduler                                      Внешний адаптер

      Event Bus переносит события между стадиями
```

Типовой поток:

1. Внешний адаптер передает данные во входной порт `collector`.
2. `collector` проверяет форму данных и выпускает событие о результате приема.
3. `knowledge` преобразует принятые данные в версионированное каноническое знание.
4. `scoring` использует согласованное знание и версию правил для формирования воспроизводимой оценки.
5. `workflow` определяет следующий допустимый шаг на основании событий и состояния процесса.
6. `publication` принимает одобренный пакет и передает его внешнему публикационному адаптеру.
7. `scheduler` может инициировать новый workflow временным триггером, не обходя его правила.

На каждом шаге должны сохраняться идентификатор корреляции, версия контракта, происхождение данных и результат обработки. Конкретные поля будут определены отдельной задачей в общих типах и событиях.

## Разрешенное направление зависимостей

- Внешние приложения (`backend`, `agents`, `workers`) могут зависеть от будущих публичных портов Alpha Core.
- Alpha Core может зависеть только от нейтральных общих контрактов, размещенных в `packages/shared-types` и `packages/shared-events`, после их утверждения.
- Инфраструктурные реализации могут реализовывать порты ядра, но ядро не знает об этих реализациях.
- `event_bus` не зависит ни от одного доменного модуля.
- `workflow` координирует модули только через их публичные порты и события.

## Запрещенные зависимости

Запрещены:

- зависимости Alpha Core от `backend`, `frontend`, `agents`, `workers`, `database`, `docker` или `infrastructure`;
- импорт внутренних реализаций одного модуля Alpha Core другим модулем;
- циклические зависимости между модулями;
- прямой доступ `collector`, `knowledge`, `scoring`, `publication`, `scheduler` или `workflow` к базе данных, Redis, брокеру сообщений, файловой системе или внешнему API;
- использование FastAPI, ORM, SDK провайдеров AI и конкретных клиентов транспорта внутри доменного ядра;
- прямой вызов `scheduler` модулей `collector`, `scoring` или `publication` в обход `workflow`;
- публикация результата до завершения предусмотренных workflow-проверок;
- передача инфраструктурных моделей и исключений через границы ядра;
- дублирование общих событий и типов внутри отдельных модулей.

## Правила дальнейшего развития

Любой новый контракт или реализация Alpha Core требует отдельной Backlog-задачи, ADR, анализа влияния и тестов контрактов. Ломающие изменения должны иметь новую версию и план миграции. До выбора контракта нельзя добавлять временные связи между модулями «для удобства».
