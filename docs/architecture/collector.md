# Архитектура Collector Framework

## Статус

- Backlog-задача: TASK-0005.
- Статус: foundation contract.
- Сетевые адаптеры и источники: отсутствуют.

## Роль Collector

Collector — входная граница Alpha Core для одного типа внешнего источника. Его задача — получить данные через внешний адаптер, сохранить их происхождение и вернуть нейтральный `CollectorResult`.

Collector не определяет, являются ли данные знанием, не рассчитывает оценки и не управляет дальнейшим процессом. Эти решения принадлежат другим модулям Alpha Core.

## Компоненты Framework

```text
CollectorRegistry
       |
       | хранит тип
       v
 BaseCollector <|-- FutureCollector
       |
       | collect()
       v
CollectorResult o-- SourceItem
       |
       | будущее событие
       v
    Knowledge
```

- `BaseCollector` фиксирует обязательный интерфейс.
- `CollectorRegistry` знает только имена и классы доступных Collectors.
- `SourceItem` переносит исходный payload и метаданные происхождения.
- `CollectorResult` фиксирует итог одного запуска.

## Жизненный цикл

1. Composition root выбирает зарегистрированный тип Collector.
2. Внешняя фабрика создаёт экземпляр и передаёт ему конфигурацию и адаптеры. Registry не участвует в создании.
3. Scheduler или workflow формирует команду запуска через будущий публичный порт.
4. Оркестратор вызывает `collect()` и ожидает `CollectorResult`.
5. Collector получает данные, формирует `SourceItem` и определяет итоговый статус запуска.
6. Оркестратор публикует версионированное событие результата через Event Bus.
7. Knowledge принимает событие и самостоятельно решает, как преобразовать данные в каноническое знание.
8. Экземпляр Collector освобождается владельцем его жизненного цикла.

Retry, timeout, rate limiting, дедупликация между запусками и планирование не входят в текущий контракт. Их владелец будет определён отдельным архитектурным решением.

## Связь с Knowledge

Направление потока данных одностороннее: Collector формирует нейтральный результат, Knowledge его потребляет. Collector не импортирует модели или реализации Knowledge и не ожидает ответа о сохранении.

Будущая связь должна проходить через версионированное событие из `packages/shared-events`. Общие идентификаторы и envelope-типы должны находиться в `packages/shared-types`. До утверждения этих контрактов прямое соединение модулей запрещено.

## Подключение нового источника

Для нового источника потребуется:

1. Создать внешний адаптер транспорта за пределами Alpha Core.
2. Создать класс, наследующий `BaseCollector`.
3. Предоставить стабильное уникальное имя.
4. Реализовать преобразование ответа адаптера в `SourceItem`.
5. Зарегистрировать класс в локальном `CollectorRegistry` внутри composition root.
6. Добавить контрактные тесты BaseCollector и тесты адаптера без обращения к реальному источнику.
7. Отдельно настроить запуск через workflow или scheduler.

Автоматическое сканирование модулей и регистрация через побочные эффекты импорта не допускаются. Регистрация должна быть явной и наблюдаемой.

## Разрешённые зависимости

Collector Framework может использовать:

- стандартную библиотеку Python;
- утверждённые нейтральные типы из `packages/shared-types`;
- утверждённые события из `packages/shared-events` после их появления.

Конкретная реализация Collector может принимать внешний адаптер через абстрактный порт, но тип транспорта не должен становиться частью `SourceItem` или `CollectorResult`.

## Запрещённые зависимости

Запрещены:

- зависимости от `backend`, `frontend`, `agents`, `workers`, `database` и `infrastructure`;
- прямые импорты из `core.knowledge`, `core.scoring`, `core.workflow`, `core.publication` и `core.scheduler`;
- зависимости framework-контрактов от FastAPI, SQLAlchemy, Redis, HTTP-клиентов, HTML-парсеров или AI SDK;
- сетевые запросы, чтение API и парсинг внутри `BaseCollector`, типов или Registry;
- создание глобального registry или автоматическая регистрация при импорте;
- хранение секретов и инфраструктурной конфигурации в типах Collector;
- передача объектов конкретного SDK через публичную границу;
- запуск Collectors самим Registry.

## Обработка ошибок

Ожидаемые ошибки отдельного источника должны быть отражены в `CollectorResult`: полный результат, частичный результат или неуспешное завершение. Неожиданные программные ошибки не должны маскироваться как успешный результат. Детальная типизация ошибок и политика retry будут добавлены отдельной задачей.
